Two industries sell AI observability. One watches the silicon, one watches the model. Neither can answer the question a platform team actually asks at 3am — and that unanswered question is the entire product.

01

The gap worth building into

Orchestr8's screens currently show Kubernetes clusters, edge fleets, security policy and AI recommendations. Calling that an "AI observability platform" is only true if you pick the right definition of the term — because in 2026 there are two, and they barely overlap.

Infrastructure observability (Datadog, Dynatrace, Grafana, New Relic) watches nodes, pods, metrics and traces. It models a GPU as a device with a utilization percentage. LLM observability (Langfuse, LangSmith, Arize, Braintrust, Helicone) watches prompts, tokens, evals and cost. It models inference as an API call and has no idea what hardware served it.

GPU utilization at 95% tells you nothing about model quality, and memory bandwidth can look healthy while inference latency silently degrades. GPU monitoring and LLM observability are complementary, not substitutes.

— AI Infrastructure Observability 2026; Towards AI, The AI Inference Stack in 2026

The failure mode both camps miss is the common one. A GPU pinned at 99% while the request queue grows and p95 time-to-first-token climbs is not healthy — it is impressively busy and failing its users. The infra tool reports a green node. The LLM tool reports slow responses with no cause. Somebody joins the two by hand, in Grafana, at 3am.

That join is the product. Everything else on the roadmap — dashboards, topology, policy — is table stakes that incumbents already ship better. The defensible thing Orchestr8 can own is the sentence that comes out the other side: "p95 TTFT breached because GPU-0a1b2c3d is thermally throttling, not because traffic rose."

02

Is the market real

Yes, and it is being funded now. The numbers below are the ones that matter for positioning — market size proves the category, the Kubernetes figure proves the deployment substrate, and the funding proves buyers are paying.

Who is already funded

Langfuse ($4M, YC, 24k GitHub stars) moved its entire product to MIT in June 2025 and was acquired by ClickHouse — a strong signal for the storage decision in §4. LangSmith ($25M, 100k+ developers), Helicone ($2M, YC), and Arize ($70M) fill out the LLM camp. Every one of them is blind below the API call.

Pricing anchors: Langfuse Core $29/mo and cloud tiers $59–$499; Braintrust Pro $249/mo; Arize $30K–$500K/yr; Datadog roughly $120/day for LLM span monitoring on top of existing APM spend. That last figure is the wedge's commercial argument — the incumbent charges a premium for the half of the picture it can see.

03

The shape of the system

Three deployables, split on where they must run rather than on taste. The collector must sit next to the hardware. The API must sit next to the data. The UI must sit next to the user. Nothing else earns a service boundary yet.

04

Stack decisions, and what they beat

Each row is a choice with a rejected alternative, because a stack defended only by what it includes is not defended at all.

Wire format
OpenTelemetry semconv v1.40.0 · GenAI still experimental

gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.response.finish_reasons give token cost and latency a vendor-neutral shape. OTel has graduated CNCF; instrumenting against it means customers can adopt Orchestr8 without ripping out what they have — the single biggest adoption lever a newcomer has against Datadog.

Not: a proprietary SDK. It would be faster to ship and would cap the company at whoever tolerates lock-in. Set OTEL_SEMCONV_STABILITY_OPT_IN to dual-emit while the conventions stabilise.

Ingest
OTel Collector, agent + gateway contrib distro

One collector handles tens of thousands of spans/sec; millions needs the tiered split. Agents stay dumb and local; the gateway does tail sampling and is the single writer to ClickHouse. Kafka slots between them when spikes outgrow the queue — later, not now.

Not: writing a custom Go collector. The contrib distro already has the DCGM scrape, the k8s attribute processor and the ClickHouse exporter. Building those again is months of work to arrive at the same place.

Storage
ClickHouse the load-bearing choice

This product's natural key is gpu_uuid × model × pod × request_id — high cardinality by definition. Prometheus creates a new series per label combination, so a single high-cardinality label can multiply the bill overnight. ClickHouse stores those as columns and compresses 10–20×, which is what makes keeping 100% of the data affordable. That ClickHouse acquired Langfuse says the category converged here already.

Not: Prometheus + Thanos. Excellent for node metrics, structurally wrong for per-request dimensions. Teams running Prometheus/Grafana at mid-scale report ~$450K/yr once engineering overhead is counted.

Query API
Go net/http, no framework

Same language as the collector ecosystem, trivial static binaries, and the concurrency model suits fan-out queries. The API is thin — ClickHouse does the aggregation, Go shapes the response and enforces the contract.

Not: FastAPI. Fine for the correlation engine's ML work later, wrong for the hot query path. Not a framework either — four endpoints do not need one.

Frontend
Next.js server components keep what exists

Roughly 70% of the current UI survives the pivot. Fetching in server components means no client data library, no loading spinner, no useEffect — and the contract is validated on the server before a component sees it.

Not: React Query or SWR. Nothing on these pages needs client-side cache invalidation yet. Add it when a live-streaming view actually demands it.

Correlation
Rules first, models later deliberately boring

The first release should ship maybe eight hand-written rules — thermal throttle, KV cache saturation, XID error, node pressure, traffic surge, model rollout. They are explainable, debuggable, and need no training data, which a new product does not have. Every verdict carries its evidence list and a confidence number the user can argue with.

Not: an LLM-as-judge or anomaly model on day one. An unexplainable verdict at 3am is worse than no verdict; it costs trust you only get to spend once.

05

Unit economics decide the architecture

Observability businesses die on storage cost, not on features. Three decisions keep the margin, and all three are architectural rather than commercial.

Tail sampling, not head sampling. Keep 100% of errored and slow spans, 10% of the boring ones. The spans you drop are the ones nobody queries; the spans that explain an incident are kept in full.

Tiered retention. Raw GenAI spans are the largest line item and live 30 days. The per-minute rollups the dashboard actually reads live 13 months and cost almost nothing — a year-over-year comparison reads the rollup, never the raw table.

Aggregate at write time. A dashboard load should be a key lookup against a materialized view, not a scan of a month of spans. One caveat worth stating because it is a common and silent bug: store a quantile sketch, not a pre-computed p95. Averaging p95s across windows produces a number that is simply wrong.

06

Business model

Open-core is the dominant pattern in this category and the only realistic route to adoption against incumbents with sales teams. The split that works — Langfuse, PostHog, Grafana all landed here — is product features open, operational features commercial.

Put tracing, GPU and inference collection, correlation rules, dashboards and alerting under MIT. Keep SSO/SCIM, audit logs, project-level RBAC, and SLAs commercial. The instinct to hold back the correlation engine is the wrong one: it is the reason anyone tries the product, and a self-hosting team that cannot see its value never converts.

Meter on GPU-hours observed rather than seats or ingested gigabytes. It tracks the customer's own cost base, it cannot be gamed by dropping telemetry, and it aligns the bill with the thing the product saves money on. Gigabyte pricing actively punishes customers for instrumenting more, which is the opposite of what you want.

07

Where the build stands

Phase 0 is done and running. The dashboard is no longer hardcoded — it renders from a Go service over a validated contract, and fails loudly with an error state when that service is down rather than quietly showing invented numbers.

Phase 0Separate and contractshipped

Monorepo split into apps/web, services/api, services/collector, packages/contracts. Zod schema and Go structs validate the same golden fixtures, so cross-language drift fails a test. Dashboard reads the API; six of nine screens still hold hardcoded arrays.

Phase 1Make one signal real

Stand up ClickHouse and the collector against a single GPU node running vLLM. Replace the fixture read in loadDashboard() with the queries in schema.sql. One real metric beats nine fake screens.

Phase 2The correlation engine

Eight rules joining gpu_minute to inference_minute. This is the demo that wins a viva and the feature that wins a customer — build it before the remaining screens.

Phase 3Migrate the rest

Extend the contract to clusters, edge, security and settings. Each screen moves from hardcoded array to endpoint using the pattern Phase 0 established.

Phase 4Close the loop

Act on correlations — drain a throttling node, rebalance a replica — through GitOps rather than direct cluster writes, so every automated action is reviewable and revertible.

08

What could sink it

HighDatadog ships this as a feature

They already have the agent on every node and the customer relationship. The defence is not technology, it is focus and price: they charge ~$120/day for LLM spans on top of APM, and correlation is a footnote in their roadmap rather than their reason to exist.

HighCorrelations that are confidently wrong

A platform team forgives a missed incident and never forgives being sent to drain a healthy node. Hence rules before models, evidence on every verdict, and a visible confidence score. Measure precision, not recall, for the first year.

MediumGenAI semantic conventions are still experimental

semconv v1.40.0 shipped February 2026 with GenAI attributes not yet stable. Dual-emit via OTEL_SEMCONV_STABILITY_OPT_IN and isolate attribute names behind the materialized-column layer so a rename is a migration, not a rewrite.

MediumNo GPU to develop against

The whole thesis rests on telemetry from hardware a student project rarely has. Mitigate with a DCGM simulator or a few hours of rented A100 time to capture a real trace once, then replay it. A recorded real trace is worth more than any amount of synthetic data.
