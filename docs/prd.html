01Problem

Two industries sell "AI observability" and neither answers the question that matters. Infrastructure APM sees nodes, pods and GPUs — it reports a GPU at 99% utilization as healthy. LLM observability sees prompts, tokens and latency — it reports slow inference with no cause, because it has no idea what hardware served the request.

The most common production failure in AI serving sits exactly between them: a GPU pinned at 99% while thermally throttling, queue depth climbing, p95 time-to-first-token breaching SLO. Utilization looks perfect. The service is failing.

The product, in one sentence

p95 TTFT on llama-3.3-70b breached its 1200ms SLO because GPU-0a1b2c3d on gpu-a-04 is thermally throttling at 88°C — not because traffic rose. Request rate is flat over the window.

Everything else in this document is table stakes that incumbents already ship better. The correlation is the product. On-call engineers currently jump between five dashboards to reach that sentence by hand.

Why now

  • 66% of organisations running GenAI inference use Kubernetes (CNCF 2026) — the substrate is settled.
  • OpenTelemetry GenAI conventions (semconv v1.40.0, Feb 2026) give token and latency telemetry a vendor-neutral shape for the first time.
  • LLM observability is $2.69B in 2026 → $9.26B by 2030, and every funded player is blind below the API call.

Non-goals

Not buildingWhy
General-purpose APMDatadog wins on breadth. We win on one question.
Prompt / eval workbenchBraintrust and LangSmith own it. Different buyer.
GPU schedulerRun:ai, Volcano, KAI already do it. We observe, we don't place.
Log aggregatorLogs are context for a correlation, never the headline.
Direct cluster mutationEvery action goes through GitOps. Non-negotiable.

  • Stop paging me for the same thermal issue three nights running.

Ships and tunes the models. Has no cluster access and wants none.

Dana — Eng Manager / Compliance tertiary

03Entry points

An observability product is almost never opened at the front door. Design for the deep link first.

#EntryTriggerLands onUser's state
E1Alert deep linkPagerDuty / Slack /correlations/{id}Stressed, 3am, needs an answer in seconds
E2Daily checkBookmark, start of shift/dashboardCalm, scanning for anything new
E3CI status checkPR check fails on scan/security/scans/{id}Blocked, wants the specific CVE
E4Teammate shareURL in incident channelAny resource URLJoining mid-incident, no context
E5Cold acquisitionMarketing → signup/onboardingEvaluating, will leave in 10 minutes
E6Scheduled reportMonthly email/reports/{id}Compliance or budget review
Build first

E1 is the highest-value entry. It must render the full correlation — symptom, cause, evidence, recommended action — with zero clicks and no further navigation.

Requirements

  • Every resource has a stable, shareable URL. Tab selections, filters and time ranges are query params, so a pasted link reproduces exactly what the sender saw.
  • Deep links survive auth. An unauthenticated hit on /correlations/abc returns to /correlations/abc, not the dashboard.
  • Time ranges pin on share. A link shared at 14:12 shows the 14:12 window forever, not "last 15 minutes" relative to the reader's clock. This is the most common way incident links become useless.
Blocking bug · E2

The sidebar's "Dashboard" item links to / — the marketing landing page, not /dashboard. Clicking it from any inner page ejects the user from the app. No resource-level routes exist at all, which blocks E1, E3 and E4.

04Exit points

Framing

For an incident tool, time-in-app is a cost, not engagement. A dashboard product optimises for dwell time. Orchestr8 optimises for getting Priya out of the building with an answer. §10 makes session duration an explicit anti-metric.

Failure exits — design these explicitly

#Failure exitTodayRequired

Principle

Orchestr8 never renders a plausible-looking number it cannot vouch for. The Phase 0 refactor deliberately removed the mock-data fallback for exactly this reason — when the API is down, the dashboard says so rather than inventing figures.

5.4 Flow D — Onboarding

Across 62 B2B SaaS companies average activation is 37.5%, and over 98% of users who never hit a value milestone churn within two weeks. Onboarding is a first-class feature, not a nicety.

The value milestone

The user sees their own GPU's real temperature. Not a tour, not a sample dashboard — their hardware, their number. Target: under 15 minutes from signup.

01

02
Waiting for telemetryLive checklist — collector ✓ / DCGM ✓ / inference engine ⋯. Must name which component hasn't reported. "No DCGM metrics from gpu-a-04" is actionable; "Waiting…" is not.

04

Resumable and re-enterable from Settings, since users add clusters months later. Offer a demo dataset for evaluators with no GPU — clearly watermarked, never mixed with real data.

06Global actions

Three buttons live in the top nav on every page. They are the product's only write paths, and all three are currently theatre.

6.1 Deploy App theatre

Current state

AspectToday
InputsEnvironment (5 hardcoded), Version (5 hardcoded), Canary toggle, Auto-rollback checkbox
Executionawait new Promise(r => setTimeout(r, 2000))
OutcomeMath.random() > 0.3 — succeeds 70% of the time, at random
TrackingNone. The deployment does not exist after the toast fades.
Delete, don't defer

The Math.random() failure is the single most misleading line in the codebase. It manufactures a failure the user cannot diagnose, cannot meaningfully retry, and which corresponds to nothing. It goes in Phase 1 — not "wired up later".

Target design

Orchestr8 never writes to a cluster directly. Deploy opens a pull request against the GitOps repo; Argo CD reconciles it. Every deployment is reviewable, revertible and auditable by construction — and the audit trail is git history, not a database table we have to defend to a compliance reviewer.

Engine: Argo Rollouts over Flagger. Flagger has no UI and promotes on metrics via a confirm-promotion webhook; Argo Rollouts assumes a human above it, and Argo CD ships health checks that understand Rollout objects. Orchestr8 is that human layer, so the tool expecting one is the right fit. v1.10.0 (Aug 2026) adds the RolloutPlugin CRD, extending progressive delivery to StatefulSets — relevant because inference servers often run as StatefulSets for KV-cache affinity.

Step 2 — Preflight, the differentiator

Runs before the gate and blocks on failure. This is where Deploy and Security Scan join up.

CheckWhat it catches
Image scanInherits the latest Trivy result for this exact digest. Unsigned or critical-CVE images block.
Policy dry-runKyverno/Gatekeeper evaluated ahead of time, so violations surface here rather than as a cryptic admission rejection.
CapacityGPU memory for the new replica set alongside the old one. A blue-green deploy of a 70B model needs 2× GPU memory; discovering that mid-rollout is an outage.
SLO budgetIs this service already burning error budget? Deploying into a live incident needs explicit override.
DiffThe actual YAML change, rendered. No blind deploys.

Steps 3–5 — Gate, rollout, verify

  • Approval gate required for production, RBAC-configurable. Regulated environments need evidence of who approved which promotion at what time, so the record captures approver identity, timestamp, diff hash, and preflight results as they stood at approval.
  • Progressive rollout — live canary ladder 10→25→50→100% showing the analysis metrics at each step. For inference these are TTFT p95, error rate, queue depth and KV-cache usage, not just HTTP 5xx. A model rollout that doubles KV-cache pressure passes a health check and fails its users.
  • Manual pause on high-risk transitions (50→100%) so automation doesn't promote a change that passed metrics but has other implications.
  • Auto-rollback with the reason — which metric, which threshold, which step.
  • Post-deploy watch window (30 min default) during which any new correlation is auto-tagged with this deployment as a candidate cause.

Acceptance criteria

  • Math.random() deleted; every failure traces to a real cause with a real message
  • No hardcoded environment or version lists — both come from the API
  • Cancelling at any step leaves zero side effects
  • A deploy is fully reconstructible from /deployments/{id} a year later
  • Preflight failure explains which check failed and links to the fix
  • Rollback reachable in one click from the deployment page

6.2 Run Security Scan theatre

Current state

AspectToday
ScopesQuick (Trivy CVEs only) · Deep (+ OPA, Falco) · Custom Scope… — no handler
ExecutionProgress bar +5% per 300ms; results on a 5s setTimeout
DataHardcoded CVE-2023-1234, CVE-2023-5678… with 2023 timestamps
FooterExport Report — no handler · Auto-Remediate — no handler

The tool names are the right instinct — Trivy, OPA and Falco are correct choices — but nothing is wired.

Target design

  • Trivy as primary. One binary covers vulnerabilities, secrets, misconfiguration, IaC and Kubernetes manifests, and generates SBOMs. Grype as optional second opinion on external-facing images: 30–40% faster on image-only scans, fewer false positives, SBOM-first.
  • Kyverno as policy engine. Plain YAML, no Rego, and it verifies image signatures and attestations natively — no stitching together Cosign, Notary and a separate admission webhook. OPA/Gatekeeper stays supported for teams already invested in Rego.
  • Falco streamed, not polled. "Runtime threats" is not a scan result — it's a live feed the scan view snapshots.
Highest-leverage feature, and it's cheap

Store the SBOM per image digest, not just the verdict. When a new CVE drops, a stored SBOM re-matches against the updated vulnerability database without rebuilding or re-pulling the image. "Are we exposed to the new Log4Shell?" becomes a database query instead of a multi-hour rebuild.

Three real scopes

ScopeRunsDurationWhen
ImageTrivy against one digestsecondsPre-deploy preflight, PR check
ClusterTrivy K8s + Kyverno audit across live workloadsminutesScheduled nightly, or on demand
CustomSelected namespaces / clusters / severity floorvariesReplaces the dead menu item

Results — designed for triage, not counting

The current three-tab split by source is wrong; it makes the user check three places to find what matters. Sort by severity × exploitability × reachability instead.

  • Reachability matters more than CVSS. A critical CVE in a package the code never calls is noise; a medium in a request-path dependency is not.
  • Group by fix availability — "12 findings, 9 have a patched version" is the actionable framing.
  • Show first-seen and age. A critical open for 40 days is a different conversation from one that landed this morning.

Wire the dead buttons

  • Export Report → SBOM (CycloneDX/SPDX), CSV, or signed PDF. This is exit X4 and compliance genuinely needs it.
  • Auto-Remediate → generates a GitOps PR bumping the base image or adding the exception. Never a direct write. Shows the diff first. If no fix exists, disabled with the reason, not silently inert.
  • Waive (new) → suppress with a mandatory reason and expiry. Permanent silent waivers are how vulnerability programmes rot.

Acceptance criteria

  • Zero hardcoded CVEs; all findings come from a real scanner run
  • Every finding links to its upstream advisory and names the fixed version
  • Results addressable at /security/scans/{id} and shareable
  • SBOM persisted per digest and re-matchable against new CVE data
  • Export opens correctly in Excel and in an SBOM tool
  • Auto-Remediate opens a real PR, or is disabled with a stated reason
  • Failed scans report why — registry auth, timeout, unreachable node — never a silent empty list

6.3 Simulate Chaos decoration

Current state, in full

<Button variant="ghost" size="sm">Simulate Chaos</Button> — no onClick, no handler. A second "Inject Chaos" button on cluster cards is equally inert.

Strategically undervalued

Chaos is how Orchestr8 proves its own correlation engine works — inject a known fault, verify the engine names it correctly and unprompted. No competitor can run that demo, and for a final-year project it is the strongest possible viva: cause a failure on purpose, watch the product explain it.

Engine: Chaos Mesh. Daemon-based, roughly 20–30% lower resource consumption than Litmus's per-experiment pods, the richest granular fault set (pod, network, IO, stress, time, kernel, DNS, HTTP), and a clean built-in dashboard. LitmusChaos wins only if multi-cluster ChaosCenter and a shared ChaosHub become requirements later.

AI-workload experiments — the differentiated set

AI inference workloads fail differently from traditional services; generic pod-kill chaos doesn't exercise those paths.

ExperimentInjectsValidates
GPU thermal throttleClock reduction via stressDoes the engine correlate TTFT breach → throttle, not → traffic?
KV-cache exhaustionLong-context request floodIs saturation predicted before request rejection?
Inference replica killPod kill on a vLLM replicaQueue drain behaviour, TTFT recovery curve
XID error injectionSimulated GPU faultIs the node drained before more requests route to it?
Edge partitionNetwork partition of an edge nodeOffline sync queue behaviour
Model rollout regressionDeliberately slower versionDoes auto-rollback trigger on TTFT, not just 5xx?

Guardrails — this feature can cause a real outage

  • Production blocked by default. Enabling requires explicit per-cluster settings plus a second approver.
  • Blast radius stated before confirmation, in plain language: "This will degrade 1 of 6 replicas of llama-3.3-70b in gcp-us-central for 5 minutes."
  • Auto-abort on SLO breach. Error-budget burn past threshold halts and reverts the experiment.
  • Dead-man's switch. Hard maximum duration; reverts if the controller loses contact.
  • Full audit record — who, what, where, when, outcome. Chaos runs are audit-grade resilience evidence.
Rename

"Simulate Chaos" sounds like a toy. Call it Resilience Test — that is the language that survives a conversation with a compliance reviewer.

Acceptance criteria

  • Button either works or is removed — no inert controls in the nav
  • Blast radius shown and confirmed before any injection
  • Production requires explicit opt-in plus second approval
  • Auto-abort verified by test
  • Every run reports at /chaos/runs/{id} whether the correlation engine identified the injected cause

7.6 Audit Ledger — /audit stub

Currently a single card reading "Blockchain-based audit logs". Nothing else.

Recommendation

Drop the blockchain. Append-only Postgres or ClickHouse with signed entries gives every property an auditor asks for — immutability, ordering, verifiability — at a fraction of the complexity. Blockchain here is a claim that invites scrutiny the project cannot repay. If tamper-evidence matters, hash-chain the entries and publish periodic checkpoints.

P0Immutable, queryable by actor / resource / time
